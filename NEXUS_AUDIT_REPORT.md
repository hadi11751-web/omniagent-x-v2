# Nexus: single-chat-model architecture and tool audit

## Architecture verified

- `src/lib/nexus.ts` is the only chat provider exposed to the product. Requests cannot select a different chat model/provider.
- `src/lib/nexusTransport.ts` is the only chat transport. It speaks the OpenAI-compatible `/chat/completions` protocol and can use either the text tool protocol or native function calling when explicitly enabled.
- `src/lib/tools/index.ts` is the single tool registry. The seven shipped tools are: `web_search`, `fetch_url`, `calculator`, `analyze_text`, `generate_image`, `generate_pdf`, and `inspect_pdf`.
- Agent mode, normal tool calling and research mode all execute through that same registry and return tool evidence to Nexus.

## Important capability boundary

"One model" means one user-facing **chat/reasoning model**. It does not mean every byte of every capability is generated by that same model.

- `generate_image` uses Google's Gemini 3.1 Flash Image service when `GEMINI_API_KEY` is configured.
- `/api/transcribe` uses Groq Whisper for microphone transcription when `GROQ_API_KEY` is configured.
- These auxiliary service models are not model-picker choices and do not replace/fail over the Nexus chat model.

This distinction is intentional and documented so the product does not make a false "one physical model does every modality" claim.

## Repair work in this deliverable

1. Added a common `runToolSafely()` boundary so an unexpected exception inside any tool becomes a structured tool failure instead of tearing down `/api/chat`.
2. Agent mode now uses the same safe tool boundary as normal chat.
3. Tool lookup is case-insensitive and whitespace-tolerant.
4. Tool instructions no longer contradict native function-calling mode.
5. Source URLs reject credential-bearing links in addition to non-http(s) schemes.
6. Nexus vision is opt-in (`NEXUS_VISION=true`) instead of being silently assumed for every arbitrary backend.
7. Added a seven-tool registry/contract test plus source-link safety tests.
8. Added an opt-in live tool smoke test for the external capabilities; it never runs during the normal test suite.
9. Updated documentation so auxiliary image/transcription service models are described accurately.

## What the local suite can prove

The normal unit/integration suite proves code paths with mocks and local fixtures. It can verify parser behavior, tool contracts, the Nexus route, PDF creation/inspection, URL safety, retry behavior and image-tool error handling.

A live provider cannot honestly be "guaranteed" by a source-code test: provider credentials, quotas, account access, model availability and upstream outages are external. The repository therefore includes an opt-in live suite rather than pretending those dependencies are deterministic.

Run the normal checks with an installed dependency tree:

```powershell
Remove-Item tsconfig.tsbuildinfo -ErrorAction SilentlyContinue
npx tsc --noEmit --incremental false
npx eslint . --max-warnings=0
npx vitest run
npx next build
npm audit --omit=dev
```

Then, with real credentials configured, run the live tool smoke:

```powershell
$env:LIVE_TOOLS_SMOKE = "1"
npx vitest run test/live/tools-live.test.ts
```

For the real Nexus backend, use the existing live test:

```powershell
$env:LIVE_NEXUS_SMOKE = "1"
npx vitest run test/live/nexus-live.test.ts
```

## External verification not claimable from this ZIP alone

- Clerk sessions and production authentication require a real Clerk environment.
- Upstash persistence/quota/concurrency require the correct production Redis URL/token pair.
- Stripe billing/webhooks require real Stripe credentials and signed events.
- Tavily/Brave/Gemini/Groq availability depends on the credentials and account state supplied to the deployment.
- A live Nexus model must be tested with the exact `NEXUS_MODEL`/`NEXUS_BASE_URL` configured by the operator.

Those are deployment/runtime facts, not source-code facts, so this audit deliberately does not label them "guaranteed" without a live run.
